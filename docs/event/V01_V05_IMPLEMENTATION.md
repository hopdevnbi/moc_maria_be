# Voucher V01–V05 — implementation and release gates

> Code implementation is separate from deployment approval. Do not interpret passing unit tests as authorization to issue live customer discounts.

## Scope

- **V01 — API recovery**: `deploy/k8s/api.yaml` allows `https://event.mocmaria.com` alongside apex/www and explicitly keeps `GIFT_EVENTS_ENABLED=false`. Event module is already imported by `AppModule`; the prior production endpoint HTTP 404 means the deployed pinned image is older than Event code. Deployment is **manual**, not ArgoCD; publishing Git is not sufficient to update that image.
- **V02 — code issuance**: additive migration `1791900300000-GiftEventCounterPins` creates a dedicated table. Authenticated reward owner can request `POST /api/v1/gift-events/me/rewards/:id/code`; response contains a fresh **six-digit code** valid at most **five minutes**. Code is never persisted or returned in wallet listing; only a keyed HMAC-SHA256 digest is stored. Minting invalidates the previous code for that reward. Expired codes can be cleaned up and recycled. Raw code must never enter URLs, logs, email or Zalo.
- **V03 — Super Admin**: `GET /api/v1/admin/gift-events/:eventId/vouchers` filters by event, issued date range, status and optional customer UUID, at most 100 per call. `PATCH /api/v1/admin/gift-events/:eventId/vouchers/:rewardId/void` requires a reason and expected version, allows only **ISSUED → VOIDED** with redemption history and admin audit; it never hard deletes issued or redeemed rights. Voucher templates continue to be configured through GiftPrizesService, with immutable award snapshots.
- **V04 — counter verification**: `POST /api/v1/staff/gift-redemptions/verify-code` and `/redeem-code` accept the six-digit code; QR endpoints are preserved. Both require authenticated staff/branch grant or Super Admin and share the existing all-branch+branch rate limit. The final DB redemption lock and one-time status change are shared with QR. Two staff cannot redeem the same reward twice.
- **V05 — product pricing**: A percentage voucher is only configurable as enabled if its `allowedServiceIds` include published catalog records. `POST /api/v1/staff/gift-redemptions/quote-code` calculates a discount using published, active `service_variants` and active `branch_services` **server prices**, not a frontend-provided total. Applying the discount through `/redeem-code` requires an explicit cashier-confirmed `saleReference` and the actual sold variant(s), recalculates under the same transaction as redemption, enforces `minSpendVnd`/`maxDiscountVnd`, and saves amount/receipt in redemption history. Migration `1791900400000-GiftVoucherReceiptUniqueness` prevents using the same receipt to redeem multiple percentage vouchers. **It does not charge the customer or assert bank/card payment success.** A staff member must verify actual paid receipt before confirming.

## Security and operational details

1. `GIFT_COUNTER_PIN_SECRET`: Kubernetes Secret `moc-maria-gift-counter` key `pin-secret`, high-entropy value at least 32 characters. Do not put secret value in Git or command arguments. This reference is optional at pod startup so absent configuration does not crash unrelated services; **PIN API fails closed** until provisioned.
2. Six digits means only one million values. Do not allow unauthenticated code lookup. Current all-branches rate limits apply to the code endpoints; assess IP/WAF thresholds and multi-actor abuse before go-live. Always require online counter authentication, live token, correct branch and non-expired reward.
3. Voucher templates are **not** voucher instances. Admin edits prizes only in DRAFT/PAUSED; changing template never edits already-issued reward snapshot. No arbitrary manual award creation, replacement, reinstatement, or hard deletion in V01–V05.
4. The quote supports products that exist in the **official backend service catalog** (`services`, `service_variants`, `branch_services`) and have been explicitly included in `allowedServiceIds`. Marketing-only drink/menu entries without a persisted catalog variant are intentionally **not eligible**, until properly seeded. Never assume static frontend menu rows are equivalent to backend stock/receipts.
5. The manual receipt is a cashier attestation, not proof of payment integration. No refund/restoration policy is implemented; cashier must not redeem a voucher before delivery of the purchased eligible items. A full POS/checkout adapter with payment verification would need a separately reviewed integration.
6. The historical report and existing voucher QR remain functional; expired-but-still-ISSUED rewards are shown as expired in the voucher Admin list without changing DB rows.

## Release sequence (not yet executed against production)

1. Build and QA immutable BE image; deploy with `GIFT_EVENTS_ENABLED=false`. Verify `GET /api/v1/gift-events/current` is HTTP 200 with status DISABLED and CORS preflight from event host succeeds without exposing other origins. Confirm booking, auth and catalog regression.
2. Create a **separate** PostgreSQL QA database, backup, and run migrations in order: `1791900000000`, `1791900100000`, `1791900200000`, `1791900300000`, `1791900400000`. Do not run these blindly on production. Rehearse down/backup recovery while QA is empty.
3. Seed one draft and a tiny fixed-stock voucher pool on QA from real catalog IDs and active branches. Provision PIN secret only through approved secret management. Run two-staff concurrent redemption, 1,000,000-code boundary/rate limit, identical receipt collision, expiry, wrong branch, out-of-budget, and request retry tests.
4. QA storefront/receipt scenario manually with an authorized Super Admin and cashier. Test iOS/Android 360px, QR and PIN, browser refresh, outbox failures, and safe rollback. Keep `GIFT_EVENTS_ENABLED=false` on production until signed off.
5. Final Event November campaign configuration must be rechecked against actual backend catalog IDs and benefit/legal/finance approval. No voucher from a mock campaign is redeemable merely by pushing code.

## Known boundaries

No local PostgreSQL server was available on `127.0.0.1:5432` at the time of implementation. The Kubernetes context on the workstation currently points to an **unrelated AWS EKS cluster**; never use it to apply Mộc Maria manifests. Mộc Maria is manually deployed to its separate VPS/K8s cluster; only an authorized release operator with the correct kubeconfig may apply migrations/images. Existing API/CORS failure must be re-probed after an actual deployment, not inferred from a successful build.
