# Administrator links into customer–KTV support

The owner confirmed that all super-admin Zalo channels receive Sơn Tùng notifications. The defect was the shared administrator formatter's fixed `/quan-tri/lich-hen` URL. The owner explicitly chose support inside the existing customer–KTV conversation, with the administrator's own identity.

New administrator inquiry alerts link to `/tin-nhan?inquiry=<persisted inquiry ID>&support=1`; chat alerts use `thread=<UUID>&support=1`. All three administrator channels share this formatter. KTV links remain participant-only and exact-provider bot routing is unchanged. The sanitizer accepts only these exact internal locator formats, including numeric UUIDs, while continuing to redact contact information.

The authenticated support entry requires an active SUPER_ADMIN with `admin.portal` and `customers.manage`. The server resolves a real persisted inquiry or thread and checks the customer, KTV user/application binding, active participants and KTV role. It reuses the exact two-party thread or creates it from a legitimate inquiry without sending any message automatically. Entry creates a 24-hour, actor-specific support grant in bounded existing metadata and an audit event. Subsequent list/history/updates/send access requires the current role and an unexpired grant. Ordinary administrators or unrelated KTV accounts gain no access. A chat with a private password cannot be opened by a third-party support actor; the thread row lock serializes access with privacy changes.

Support messages retain the real administrator `sender_user_id`, show their actual display name and a “Hỗ trợ Mộc Maria” label for every viewer, and create a separate audit event once. No KTV/customer impersonation occurs. Existing blocking, image ownership, rate limits, transactional outboxes and client-message idempotency apply. Supporting administrators cannot manage participant block/password controls, and their read acknowledgments never advance the customer's or KTV's read cursor. A committed support reply notifies both original participants with an honest support label; external staff bots continue to receive only inbound buyer messages. Administrator bot delivery remains unchanged and protected text never reaches Zalo.

The frontend preserves the full support locator through login, uses the explicit support endpoint and shows support mode clearly. Existing KTV/customer URLs and denial behavior remain intact. Previously delivered Zalo messages retain their original URL; this release changes newly formatted notifications and does not replay old messages.

Validation includes real isolated PostgreSQL HTTP coverage for exact-thread entry, denial before enrollment, ordinary-admin/unrelated-KTV rejection, honest support messages, retries/audit deduplication, read-cursor isolation, expiry, live role revocation, blocks and password-protected conversations. Frontend tests cover login returnTo, both locator forms and sender labels for participants/supporting admins. No production booking, chat or test notification is fabricated. No role assignment, schema migration, bot recipient/Secret or other tenant changes are required. Release IDs and final checks are in `deploy/admin-inquiry-support-release.json`.
