# Booking availability foundation — E1

Status: implementation and isolated acceptance in progress. Production remains verified D2 until an E1 release record is appended.

Migration15 BookingAvailabilityFoundation1791646000000 adds explicit per-variant/branch/mode settings and appointment/item/staff/resource/quote/status-history tables and entities. It does not create appointments or business fixtures. Source rollback preserves additive tables after real writes.

Owners configure slot step, lead time, horizon, request lifetime and actual resource requirements with explicit confirmation/reason. Missing or disabled configuration returns no slots. An empty resource list means the owner explicitly checked that this package needs no room/equipment allocation. AT_HOME on-site resources are rejected; geographic boundaries/address validation and request writes are E2 work.

GET /availability takes variantId, branchId, date (YYYY-MM-DD Vietnam calendar date), optional providerApplicationId. It intersects active public catalog/mapping, approved active provider account, current consent/contact verification, reviewed public profile/quality, service-specific training/legal scope, active branch assignment, weekly/date-override/time-off, branch hours/exception days, duration and both preparation buffers. Certificates/legal grants/policy must remain effective through the blocked end time. Mode AT_BRANCH maps to reviewed provider policy ON_SITE.

Existing provider reservations are subtracted globally across branches, not just the selected branch. REQUESTED/ACCEPTED/CUSTOMER_CONFIRMED rows occupy capacity only until their request expiry; CONFIRMED/CHECKED_IN/IN_SERVICE/COMPLETED intervals stay reserved. CANCELLED/DECLINED/EXPIRED/NO_SHOW do not consume future capacity. Resource occupancy uses the actual peak of half-open intervals; sequential bookings are not incorrectly summed. Allocation and provider ordering are deterministic.

Times persist as timestamptz/UTC; all schedule/date calculations use Asia/Ho_Chi_Minh, independent of the host timezone. Candidate service starts align to the configured minute grid and preparation fits inside both provider and branch windows. Overnight schedules are not inferred from the existing same-day schedule model.

GET /availability/earliest returns the earliest candidate in at most14 consecutive dates from the supplied date and includes search.fromDate/throughDate/hasMoreDates. It does not claim the rest of the owner horizon is empty. Both public routes are no-store and return safe name/time/price fields only; no appointment IDs, resource allocation, private consent/contact/legal references or personal contact/address information. A read uses a REPEATABLE READ database transaction. Provider trust and schedule accept that transaction manager.

These are planning previews: reservation=false and requestEnabled=false. No appointment creation/confirmation/status/reschedule/cancellation writes are exposed in E1. An availability response must never be treated as a held slot. E2 must acquire canonical provider/course/branch/catalog/resource locks, revalidate eligibility and current price and check conflicts inside the write transaction with idempotency and explicit quote acceptance. AT_HOME must verify server-owned reviewed geographic boundaries as well as radius; a customer-supplied jurisdiction string alone is insufficient.

Admin settings: GET /admin/booking-settings requires staff.manage; POST requires roles.manage and explicit configurationConfirmed/reason. Responses are private,no-store. Every settings write locks the branch and appends an audit record including previous settings. FE exposes the configuration beneath each existing catalog variant; no guessed business settings are prefilled.
